The problem

Agent sprawl is a bookkeeping problem, not a tooling problem

Most teams now have MCP servers, prompt skills, autonomous agents and internal AI apps running in production. Nobody has one place that answers: who owns this, what does it cost, who is allowed to call it, and what happened last Tuesday.

Five ledgers, no ledger

Observability tools watch traces. IAM tools issue credentials. Cost tools read invoices. None of them agree on what an "asset" is — so nothing can be retired.

Totals don't cut costs

"Spend is up 30%" is not an answer. You need to attribute it to department × agent × skill before you can act on it.

SaaS can't hold your keys

Source code, prompts, tool credentials and audit logs sit inside your firewall. Most AI tooling today assumes the opposite.

The differentiator

Cost attribution, not cost observation

Trace viewers tell you what happened. YBK tells you which department, which agent, and which skill is responsible — the three axes you need to actually cut a number.

Governance

One ledger, one identity, one audit trail

MCP services, Skills, Agents, AI apps and NAS hosts all live in the same inventory with the same lifecycle state machine — so retiring a stale agent is a state change, not a scavenger hunt.

Lifecycle state machine

Draft → registered → active → deprecated → retired, with dependency topology so you can see the blast radius before you change anything.

94 permission points

Fine-grained resource.action permissions enforced server-side on 499 REST routes and 98 MCP tools. Read and write are genuinely separated.

Immutable audit log

Every mutation records actor, target, before/after and approval chain. Exports as JSON for your SIEM.

Approval workflows

Registering or promoting an asset routes through approvers. Demo data includes real approval chains.

FAQ

Questions people actually ask

Is this another "AI governance" wrapper on top of an LLM gateway?

No — and the distinction matters. LLM gateways sit in the request path. YBK sits in the inventory layer: it knows what assets exist, what they cost, who owns them and what their blast radius is when you change them. Many teams run both.

How is this different from a trace viewer like LangSmith or Helicone?

They answer "what happened in this request". YBK answers "which department, agent and skill is responsible for this spend, and who approved running it". Trace data is an input to that question, not the answer.

Who maintains it?

One person. That is a real limitation and worth stating plainly. The mitigations are architectural rather than promissory: MIT source you can read today, self-hosting so nothing breaks if I disappear, and 2010 assertions in CI so regressions surface immediately.

Does it support multi-tenant / SaaS deployment?

The architecture supports org-level isolation and there is a five-platform theme system, but the hosted SaaS path is not the product today. The product is the self-hosted instance you run inside your own network.

Is the demo I can click the real product?

It is the real product running against seeded data in read-only mode. Write operations return 405 by design. To try writes, self-host it.

What about credential hosting and rotation?

Long-lived third-party credentials (API keys, internal service tokens) now have a platform home: registered values are AES-256-GCM encrypted at rest, retrieval requires a dedicated permission point (app.credential.fetch) with per-access audit, and rotation is a same-key overwrite (old value invalid immediately). Short-lived workload identity (SPIFFE-style) for agent runtimes remains on the roadmap; agent platform identities today use rotatable machine credentials.
