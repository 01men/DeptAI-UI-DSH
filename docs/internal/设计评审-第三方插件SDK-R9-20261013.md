## 一、现状盘点（榕器）

### 1.1 plugin-ctx：进程内能力白名单代理

`packages/platform-core/src/plugin-ctx.ts`（81 行）是第三方插件运行边界的第 1 层防线，文件头明示其范围：**只做事件源鉴别 + 能力裁剪，不做模块级沙箱**（require/fs/net 隔离划归生态设计 v1.2 第 10 步 L1）。实际边界：

- **可代理的能力**（`CAPABILITY_SERVICES`，第 12-18 行）：共 5 个能力词条，其中仅 2 个映射到真实 ctx 服务——`model-gateway.invoke → modelGateway`、`usage.meter → usage`；`knowledgebase.read / audit.emit / storage.scoped` 映射为空数组，即这三个能力词条目前不授权任何 ctx 服务（它们的价值在运行时对账：`plugin-market/src/index.ts` 第 202-205 行的 `CAPABILITY_RESOURCE_MAP` 把 `model-gateway.invoke → model:*`、`knowledgebase.read → kb:*` 作为 usage 计量授权基线）。
- **事件面收敛**：`platformBus.emit` 强制事件名收敛到 `plugin:<id>:` 前缀、强制盖 `source: plugin:<id>`（第 39-44 行）；总线侧第二道校验在 `packages/platform-core/src/bus.ts`（平台保留命名空间对 plugin 来源一律拒绝，`PLATFORM_RESERVED_PREFIXES`）。
- **服务面裁剪**：`service(name)` 按 approved capabilities 判定后**直接返回 ctx 上的原服务对象引用**（第 61-66 行，`(ctx as Record<string, unknown>)[name]`）——同进程同地址空间，无任何隔离层；且 `'*'` 通配能力可放行一切（第 58 行）。
- **真实调用方只有自检端点**：`createPluginContext` 的唯一运行时消费点是 `packages/plugin-console/src/routes/market.ts` 第 154-168 行的 `/api/market/sandbox-check`（插件开发者联调自检），并未用于装载任何第三方代码——因为市场目前只受理 L0。
- **三层防线定位**（文件头声明）：代理 ctx（运行时强制）→ lint/静态扫描（明示可绕过）→ 运行时对账（usage 事件 principal/resource vs manifest 能力声明，偏差告警下架）。本评审的关注点在第 1 层的天花板：它是**授权**层，不是**隔离**层。

### 1.2 市场安装链路：五面 YAML → 提交 → 审批 → 安装 → 装配

`packages/plugin-market/src/index.ts`。需要先澄清两套「五面」：

- **第三方提交五面**（`REQUIRED_FILES`，第 104 行）：`plugin.yaml + manifest/{permissions,api,events,billing}.yaml`——注意**不含 ui.yaml**；`plugin.yaml` 携带 `sandbox / capabilities_request / content.prompts`（提示词包是 L0 唯一行为载体）。
- **自营包清单五面**：`plugin.yaml + manifest/{api,events,permissions,ui}.yaml`，由 `scripts/gen-manifests.mjs`（第 520-533 行）生成，供 lint 对账。`ui.yaml` 目前只表达 `routes`（hash 路由清单）与 `menus`，且**没有运行时消费者**——控制台侧边导航是硬编码常量（`packages/plugin-console/public/js/app.js` 的 `NAV`），ui.yaml 的「控制台按此注入导航」是文档性约定而非装配事实。

链路本身已闭环且带强门禁，逐环节如下：

1. **提交**：Ed25519 开发者身份 + 五面指纹验签（`submit`，第 298-327 行；版本不可变，同 id@version 重复提交拒绝）；
2. **门禁**：硬性 L0-only——`parseManifest` 第 150-152 行，`sandbox !== 'L0'` 直接拒绝，杜绝「内部信任」例外；
3. **静态扫描**：`CONTENT_BLOCK_RULES`（第 107-112 行）拦截疑似破坏性命令/明文密钥/动态执行/模块加载；
4. **审批**：两级审批（approve/reject），上架后内容变更（contentHash 漂移）强制重走审批，suspend 时存量安装批量联动挂起（`suspend`，第 345-353 行）；
5. **安装**：能力与权限双重 `approved ⊆ requested` 校验〔权限面是 QA E-02 修复补上的，第 378-384 行〕+ `usage.grantCapabilities` 固化授权基线 + 零价快照计量登记（`install`，第 361-421 行）；
6. **装配**：L0 运行时 = `promptPacks()`/`meterPromptUse()`（第 436/449 行），Agent 读提示词包并计量。

**装配的终点是数据，不是代码**：第三方目前没有任何可执行面。

### 1.3 rq-card：浏览器半插件（唯一已验证的 UI 注入形态）

`packages/plugin-rq-card` 是 dsh 双面插件（`package.json` 的 `dsh.client` 声明 + `exports['./client']` 指向 `lib/client.js`）：

- **宿主半**（`src/index.ts`）：空 apply 只为入 cordis loader 图；`summarizeForToolResult()` 提供 markdown 兜底契约——客户端富卡片挂掉时用户体验回落纯文本。
- **浏览器半构建**（`build.mjs`）：esbuild 单文件 CJS bundle，包装成 closure-factory 形状 `window.__ModuleLoader__.load({ id, factory(require) })`（第 151-157 行）；external 表 = `PLATFORM_MODULES`（react/cordis/dsh-client-ui-* 等 10 项，第 45-52 行）；**纯度门禁**（`purityGate`，第 106-120 行）：`@deepseek-ai/*` 只允许 type-only import，值导入直接构建报错。这是全仓唯一带构建步骤的包，且 esbuild 二进制只能借用 dsh 检出或自装（diff=0 铁律，文件头注释）。
- **浏览器半运行**（`src/client/index.ts`）：向 dsh slots 注册 `tool.call.toolview`（键位槽，逐工具名）、`conversation.chat.assistant-actions`（列表槽，反馈条）、`shell.overlay`（降级角标）；六条降级预案逐条落实（specDynamic 探测、apply 全 try/catch 等）。
- **数据回流**（`src/wire.ts`）：同源 REST `POST /rq/api/usage/feedback`——复用 plugin-dsh-bridge 挂载的 `/rq` 前缀与 `rq_sid` Cookie 鉴权，不新增宿主 RPC 通道。
- **装载约束**（`docs/internal/spike-dsh-client-capability.md`）：client-modules 伺服 `/plugins/<包名>/client.js`，激活期缺产物 = 宿主启动失败（MissingClientBundleError）；loader 条目必须是 node_modules 可解析包名。

### 1.4 宿主形态与零构建约束

- **双宿主一份代码**：`src/main.ts`（独立宿主，自起 httpServer）与 dsh 宿主（`plugin-dsh-bridge` 把榕器数据面整体挂进 dsh webServer 的 `/rq` 前缀，单进程单监听器）共享 `src/boot-all.ts` 的同一棵 cordis 插件树。**所有榕器插件进程内运行**，cordis 无插件级沙箱语义（roadmap-9-10 第 10 步自认）。
- **零构建约束**：`package.json` engines `node >= 22.6`（原生 TS 运行）；console/panel 均为原生 ES Modules，无打包器。rq-card 的构建步骤是特例且被 spike 门禁约束。

## 二、paperclip 模式摘要（参考，不复制代码）

### 2.1 plugins-sdk 的进程外执行隔离（`packages/plugins/sdk` + `server/src/services/plugin-worker-manager.ts`）

1. **每插件一进程**：宿主为每个已安装插件 fork 一个 Node worker 子进程（`plugin-worker-manager.ts` 第 2923-2936 行 `spawnProcess()` 用 `child_process.fork`）；PLUGIN_SPEC.md §12.1 明示动机：故障隔离、日志边界、资源限额、比进程内执行更干净的信任边界。
2. **stdio 上的 JSON-RPC 2.0**：worker 侧 `sdk/src/worker-rpc-host.ts` 从 stdin 读请求/向 stdout 写响应（文件头消息流图）；协议类型集中在 `sdk/src/protocol.ts`（2670 行，双方法表 host↔worker）。
3. **宿主职责与故障策略**（PLUGIN_SPEC §12.2/§12.4/§12.5）：能力执行、进程监督、job 调度归宿主；worker 失败只标记该插件 error + 有界退避重启，不拖垮实例；优雅停机 10s → SIGTERM → SIGKILL 阶梯。
4. **装载形态有诚实边界**：README「Current deployment caveats」承认 worker 与 UI 今天都是**可信代码**，运行时安装依赖可写文件系统 + npm 可用 + 注册表网络——多实例云部署尚需共享工件模型。
5. **安装源防护**（`server/src/services/plugin-install-guard.ts`）：云托管实例强制只允许装捆绑目录内的插件；所有 localPath 先 realpath 规范化（防 `..`/symlink 逃逸）再进 loader。

### 2.2 能力声明与门控

1. **manifest 声明、双点执行**：`manifest.capabilities` 声明；安装时 `plugin-capability-validator.ts` 的 `validateManifestCapabilities()` 校验「声明了 tools/jobs/UI slots 就必须有对应能力」；运行时每次 worker→host 桥调用都过 `checkOperation/assertOperation`（操作→必需能力映射表 `OPERATION_CAPABILITIES`），缺能力即 403。
2. **SDK 侧同一套门控**：`sdk/src/host-client-factory.ts` 为宿主侧 handler 工厂，越权抛 `CapabilityDeniedError`（JSON-RPC 错误码 `CAPABILITY_DENIED`）；另有 `InvocationScopeDeniedError` 强制公司作用域一致（插件不能跨公司取数）。
3. **能力词表细粒度分组**（README Capabilities 表）：约 80 个能力按 Company/Instance/Runtime/Agent/UI 五组——含 `ui.sidebar.register`、`ui.detailTab.register` 等 UI 注册能力，与宿主 API 一一对应。
4. **关键架构事实**：门控在**宿主进程**执行，worker 里插件代码物理上只有 stdio 一条通道——绕过门控等于绕过整条 IPC，不存在「拿到 ctx 对象后向上摸」的路径。

### 2.3 UI 贡献通道

1. **slots + launchers 双面声明**：`manifest.ui.slots`（page/sidebar/settingsPage/dashboardWidget/detailTab/toolbarButton/commentAnnotation 等十余种槽型，带 `entityTypes` 上下文限定）+ `manifest.ui.launchers`（宿主渲染的入口按钮/菜单项，action ∈ navigate/openDrawer/performAction 等）。
2. **UI bundle 同源伺服**：`server/src/routes/plugin-ui-static.ts` 从 `/_plugins/:pluginId/ui/*` 伺服预构建 ESM，路径穿越校验 + 仅 ready 状态插件可伺服；宿主动态 import 解析 `ui.slots[].exportName` 挂载。
3. **桥接 hooks 走 HTTP**：`sdk/src/ui/hooks.ts` 的 `usePluginData/usePluginAction` 等是薄壳，实际实现由宿主经全局 `__paperclipPluginBridge__` 注入（`sdk/src/ui/runtime.ts`），落点是 `POST /api/plugins/:id/bridge/{data,action}` + SSE `/bridge/stream/:channel`（`server/src/routes/plugins.ts` 第 510-514 行）→ 宿主再经 JSON-RPC 转发 worker。UI 组件本身不持有任何平台凭据。
4. **明示的信任缺口**：README/PLUGIN_SPEC 均承认 plugin UI 是**同源 JavaScript，能力声明不是前端沙箱**；不可信市场代码需要 worker 沙箱 + 隔离 UI，列为 future work——与榕器「L1 前不放开有码插件」的立场同构。

## 三、差距分析

### 3.1 进程内代理 vs 进程外 worker：安全边界差距

| 维度 | 榕器 plugin-ctx | paperclip worker | 差距判定 |
|---|---|---|---|
| 代码可达面 | 插件与平台同进程同堆；`service()` 返回原对象引用，globalThis/process/fs 均物理可达 | worker 独立进程，平台面只剩 stdio 通道 | **结构性差距**：代理 ctx 是授权层不是隔离层（其文件头已自认） |
| 门控执行点 | 插件侧代理对象（同进程内可被绕过：另取 `ctx` 引用、原型链） | 宿主进程、每次桥调用强制（插件无法短路面） | paperclip 的门控不可绕过性来自物理边界 |
| 故障隔离 | 第三方代码崩溃 = 平台崩溃（当前无第三方代码，风险未兑现） | 单插件 error + 有界退避，实例存活 | 榕器无故障隔离语义 |
| 资源限额 | 无（roadmap 第 10 步计划 CPU/内存/事件令牌桶） | 进程级可配（内存/CPU/停机宽限） | 榕器缺位，已有设计未实现 |
| 装载产物 | 无代码装载（L0 提示词包） | npm 包/localPath，运行时安装 | 榕器私有化部署**不能**接受运行时 npm 依赖（paperclip 自己也把这点列为 caveat） |

**缓解性事实**：榕器市场 L0 硬门禁使上述差距目前是「未兑现的潜在面」而非现行漏洞——第三方有码提交在 `parseManifest` 即被拒。另一处已对齐的事实是**事件面**：榕器的命名空间收敛 + source 双层校验（plugin-ctx + bus.ts）与 paperclip 的 `plugin.<id>.<event>` 自动命名空间等效，事件治理不是差距项。真正的问题是：一旦第 10 步 L1 立项，**进程内路线（vm.SourceTextModule）与进程外路线（worker/子进程）的选择**从未与 paperclip 证据对齐过评审，见 §4.2。

### 3.2 UI 贡献面缺口

- **第三方契约无 UI 面**：`REQUIRED_FILES` 不含 ui.yaml；第三方插件即使想贡献一个菜单项也无声明通道。
- **ui.yaml 表达力仅 routes+menus，且零运行时**：控制台导航硬编码（app.js `NAV`），「按此注入导航」未发生；无组件挂载、无槽位、无数据端点声明。
- **rq-card 已验证的机制是第一方专享**：client-modules 装载链（包名 loader 条目 → `/plugins/<id>/client.js` 伺服 → `__ModuleLoader__` 工厂执行 → slots 注册）与同源 REST 回流（`/rq` 前缀 + Cookie）都真实跑通，但入口在 dsh 侧、构建依赖 esbuild、且只服务本仓包；市场安装记录（`PluginInstallRecord`）与浏览器半装载之间没有任何接线。
- **对照 paperclip**：其 slots/launchers 声明 + 桥接 hooks + 同源 bundle 伺服是一套可借鉴的「声明-装载-数据回流」三段式；但 paperclip 的 UI 同样不是沙箱（同源 JS），这点必须在榕器方案里显式承袭而非回避。

## 四、评审结论与建议架构

### 4.1 UI 贡献面（建议列为下一步可实现项）

**可行路径：把 rq-card 已验证的 client-modules 形态泛化为「第三方 UI 贡献」，分两档实现。**

第一档（声明式 UI，无需第三方代码，复用既有审批链）：
1. 扩展第三方契约：`plugin.yaml` 的 `content` 增设 `cards`（提示词包的伴随呈现：标题/字段/链接规则），或在五面外新增 `manifest/ui.yaml` 面并进 `REQUIRED_FILES`——由 dsh 会话的 GenericToolCard/console 页面骨架按声明渲染（paperclip settingsPage 的「JSON Schema 自动生成表单」同思路，见其 README）。示例场景：合同审查提示词包附带一张「审查意见表」卡片骨架，字段清单全部声明式。
2. 好处：零新攻击面（渲染者是平台代码）、零构建（纯 YAML）、审批链（contentHash 变更强制重审，`plugin-market/src/index.ts` 第 81-82 行）原样生效；且 L0 现有供给（自营三包）可直接受益，不必等 L1。

第二档（有码 UI，白名单模块形态，泛化 rq-card）：
1. **装载**：宿主侧（dsh = client-modules 既有路径；独立宿主 = platform-core httpServer 增设 `/plugins/<id>/client.js` 伺服，对齐 spike 已证的包名解析约束）按 `PluginInstallRecord.status === 'running'` 下发浏览器半，装载产物指纹纳入五面指纹签名（防「审批的声明」与「下发的 bundle」不一致）。
2. **运行边界**：承袭 rq-card 纯度门禁形态——平台模块表（external 白名单）+ 第三方值导入只许自身内联；市场提交时静态扫描（扩展 `CONTENT_BLOCK_RULES` 至 bundle 产物）。
3. **数据回流**：只许调用 `manifest/ui.yaml` 声明的端点集（approved ⊆ requested 同口径），走既有同源 REST + Cookie 鉴权 + usage 归因——UI 组件不持有任何独立凭据（paperclip 桥接模式：UI 无凭据、全部经宿主转发）。

**沙箱边界取舍：原生 ES 模块白名单（推荐起步）vs iframe/postMessage（后续增强）。**

- iframe/postMessage——真隔离（独立 origin，Cookie 不可达），但代价高：
  - dsh slots 是 React 组件位，iframe 需包装层（高度协商/样式桥/令牌传递），注入粒度失真；
  - 与 client-modules 装载链不兼容，需另起伺服面与加载协议；
  - 零构建约束下第三方还得自带构建链才能产出 iframe 文档，门槛反而抬高。
- 原生 ES 模块白名单——授权边界而非隔离边界，但工程连续性好：
  - 与 rq-card 形态连续（client-modules + closure-factory + 平台模块表均已验证）；
  - 零构建可兼容：要求第三方提交原生 ESM `.js`，平台免构建直接伺服；TS 产物由开发者自备构建并在提交时附产物指纹；
  - 审批链（签名 + 审批 + 安装确认）提供与 paperclip 同级的「可信代码」姿态。
- **建议**：起步用模块白名单 + 声明端点回流，并在市场文档明示「这是授权边界不是隔离边界」（与 paperclip README 同等诚实的 caveat）；iframe 沙箱作为不可信供给出现时的增强项挂账，不进第一档/第二档。

### 4.2 进程外执行（列专项，对齐生态设计第 10 步）

**路线对比（worker_threads vs 子进程 vs WebAssembly）：**

| 路线 | 隔离强度 | 与零构建相容性 | 主要代价 | 判定 |
|---|---|---|---|---|
| 子进程 fork + stdio JSON-RPC（paperclip 实证） | OS 级：独立地址空间，可叠 cgroups/降权 | 好：Node≥22.6 子进程可同参数跑原生 TS | 每插件一进程；需监督/停机策略；dsh 形态下进程数膨胀 | **推荐基线** |
| worker_threads | 仅事件循环/故障隔离；同进程凭据、fs/net 全通；逃逸面大（无模块加载控制时 require 内建直达） | 好 | 内存共享需谨慎；资源限额弱 | 不推荐做安全边界，可做 CPU 密集辅助 |
| vm.SourceTextModule（roadmap 现方案之一） | 模块图级：import 白名单可强，但原型链/全局逃逸是已文档化的持久攻防面；需 `--experimental-vm-modules` | 好（进程内） | 自研负担重；roadmap 已自认「或 worker 隔离」 | 可作过渡，不建议为终态 |
| WebAssembly（wasi / QuickJS-wasm） | 最强（第二运行时） | 差：插件生态无法复用平台 TS 契约；工具链重 | 双运行时维护、性能与调试成本 | 排除 |

**与零构建约束的相容性**：子进程路线下 worker 入口可以是原生 `.ts`（Node≥22.6 `--experimental-strip-types`，与宿主同引擎同参数），宿主与 worker 间协议建议直接抄 JSON-RPC over stdio 的消息形状（`protocol.ts` 的信封设计已公开验证，不复制实现）；模块白名单（roadmap 第 10 步第 2 条：import 只解析受控模块表）落在 worker 内的装载器。

**dsh 宿主形态下的边界（专项必须回答的三个问题）**：
1. **进程归属**：榕器插件树今天活在 dsh web 进程内；worker 子进程的父进程应是谁（dsh 进程 vs 榕器自管）——dsh 重启会孤儿化 worker，监督器必须落 platform-core 而非 dsh；
2. **安装产物形态**：私有化部署拒绝运行时 npm（paperclip 教训，README caveat + install-guard 的云白名单是它的补丁）——榕器应走「市场签名产物入库（opsStorage）→ 安装时落盘 → fork 加载」的离线工件模式，天然复用 Ed25519 验签基建；
3. **失败语义**：单插件 worker 崩溃只 suspend 该插件（复用审批中心 suspend 流转），绝不拖垮 dsh web——这是进程外化换来的核心收益，须写进专项验收。

## 五、结论

1. **本迭代（R9）边界**：不实施任何 SDK、沙箱、UI 贡献装载代码；不改动五面 YAML schema 与市场门禁；本文档为唯一产出。现状的「L0-only + 三层防线」组合在无有码供给阶段是**恰当的**，无需提前加固。
2. **UI 贡献面**＝下一步可实现项：建议按 §4.1 两档推进（第一档声明式 UI 可独立小迭代立项；第二档白名单模块 UI 依赖装载接线与端点白名单）。触发条件：出现 ≥1 个真实第三方 UI 场景需求（企业客户询盘或自营插件需要会话卡片/面板卡片），且 L0 市场供给稳定（自营三包 + 第三方提交在架）。
3. **进程外执行**＝独立专项：对齐生态设计 v1.2 第 10 步（roadmap-9-10 已列触发条件：自营 L0 付费转化 ≥3 单 / 开发者 waitlist ≥20 / 企业询盘 ≥5，满足其一即立项）。专项基线建议：子进程 fork + stdio JSON-RPC + worker 内模块白名单 + 离线签名工件装载；WebAssembly 排除；worker_threads 不作安全边界。
4. **先行无风险预备**（可在专项启动前做，均不引入运行时面）：五面 YAML 扩展字段的 schema 设计稿（§4.3 R-4 清单）；能力词表演进规则冻结；`'*'` 通配能力的处置决议。
